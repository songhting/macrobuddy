# MCP 工具契约 · mcp-tools.md

本文件记录 MacroBuddy 在实际调用中依赖的工具行为、调用顺序与错误处理。

> **重要**：各 Tool 的完整参数签名以麦当劳官方文档为准
> （<https://github.com/M-China/mcd-mcp-server>）。本文只记录本 Skill 实际依赖的
> **语义契约**——即"这个工具能提供什么、输出如何被消费、什么情况下不可用"。
> 未在官方文档中确认的字段一律不使用。

---

## 1. 调用顺序原则

```
时间上下文 → 门店 → 领券 → 取券 → 菜单 → 套餐详情 → 营养 → 价格校验 → 下单
```

三个不可打乱的约束：

1. **`auto-bind-coupons` 必须在取券之前**。它领取的是"可领未领"的券，
   若在报价之后再领，前面的报价全部作废。
2. **`query-meals` 必须早于 `list-nutrition-foods`**。营养数据以当前门店
   实际在售餐品为范围，脱离菜单去取营养没有意义。
3. **`calculate-price` 必须晚于本地优化**。它是对本地算法结果的权威校验，
   不是输入。

## 2. 工具语义契约

### 2.1 `now-time-info`

- **提供**：当前完整时间信息（日期与时间）。
- **用途**：判定所处餐段（早餐 / 正餐 / 夜宵），决定单餐目标如何摊分；
  判断券的时段可用性；判断活动是否在进行中。
- **不可用时**：回退使用本地系统时间，并在输出中注明"时间来自本地"。

### 2.2 门店类

| Tool | 提供 | 用途 |
|---|---|---|
| `query-nearby-stores` | 指定地址附近的门店 | 到店取餐定门店 |
| `delivery-query-stores` | 收货地址附近可配送门店 | 麦乐送定门店 |
| `delivery-query-addresses` | 用户已创建的配送地址列表 | 复用地址，避免重复录入 |
| `delivery-create-address` | 新建配送地址的结果 | 无可用地址时补录 |

- **注意**：到店取餐与麦乐送是两个独立分支，不要混用门店列表。
- **多门店场景**：若地址附近有多家店，菜单与券可能不同，必须让用户选定一家再审。

### 2.3 菜单与营养

| Tool | 提供 | 消费方式 |
|---|---|---|
| `query-meals` | 当前门店可售餐品（分类、餐品编码、标签） | 归一化为 `MenuItem` 的 `sku`/`name`/`category` |
| `query-meal-detail` | 按餐品编码查套餐组成与可替换项 | 展开套餐结构；识别可替换的小食/饮品 |
| `list-nutrition-foods` | 餐品营养（能量、蛋白质、脂肪、碳水、钠、钙） | 填充 `MenuItem` 的营养字段 |

- **品类归一化**：官方分类名与本 Skill 的 `main/side/drink/dessert` 需要映射。
  映射表应放在调用侧，不要改算法内部约定。
- **营养数据缺失**：若某餐品无营养数据，**不得估算**，应把该餐品排除出候选集，
  并在输出中说明"因缺少营养数据未纳入"。
- **`calcium` 字段**：本版本未使用，保留以便后续扩展。

### 2.4 优惠券

| Tool | 提供 | 用途 |
|---|---|---|
| `auto-bind-coupons` | 自动领取麦麦省全部当前可领券 | **取值链路第一步**，无参数 |
| `query-my-coupons` | 账户下可用券列表 | 供优化器比价 |
| `query-store-coupons` | 当前门店可用券列表 | 门店维度可用性校验 |

- **券的归一化**：需映射到 `Coupon` 的 `discount_type`（`amount` / `percent`）、
  `value`、`min_spend`、`max_discount`、适用品类或 SKU。
- **不叠加原则**：本 Skill 按"一次只允许用一张券、取减免最大者"处理，
  与真实券包的多数规则一致。若官方后续支持叠加，应在此处改造并补充单测。
- **券门槛**：`min_spend` 判定以**套餐价生效后的 subtotal** 为准，
  不能用单品价之和，否则会错误放行"看似达到门槛"的券。

### 2.5 价格与交易

| Tool | 提供 | 用途 |
|---|---|---|
| `calculate-price` | 按商品列表（可含券）计算金额、配送费、优惠、应付总价 | 交叉校验本地算法 |
| `create-order` | 订单详情与支付链接 | 二次确认后下单 |
| `cancel-order` | 取消结果 | 用户反悔 |
| `query-order` | 订单状态、内容、配送信息 | 下单后跟踪 |
| `order-list` | 近期到店/外送历史订单 | 复购"上次那单" |

- **交叉校验的意义**：本地算法维护的是券规则的近似模型。当 `calculate-price`
  返回的实付与本地结果不一致时，**以 MCP 返回为准**，并在输出中记录差异，
  同时把该差异作为后续修正本地券规则的依据。
- **写操作前置条件**：`create-order` 与 `cancel-order` 均需用户显式确认。
  确认前必须复述门店、取餐方式、餐品清单与实付金额。

## 3. 错误处理

| 错误码 | 含义 | 处理 |
|---|---|---|
| `401` | Token 无效、已过期或未提供 | 立即停止计算，引导用户检查 `Authorization` 头与 Token。**不得用虚构数据继续** |
| `429` | 超过 600 次/分钟限流 | 退避重试；提示用户限流限制。本 Skill 单次交互仅个位数调用，正常不触发 |

### 其他异常

| 情况 | 处理 |
|---|---|
| 工具未返回结果或返回空集 | 如实告知用户，不猜测、不用示例数据顶替 |
| 门店已打烊 / 餐品售罄 | 提示用户，建议换门店或换时段 |
| 券匹配失败 | 退化为单品价 + 套餐价方案，明确说明未用券 |
| MCP 连接器未启用 | 引导完成配置后终止本次计算 |

## 4. 配额优化说明

`optimize()` 会枚举 `主食数 × (小食数+1) × (饮品数+1)` 个组合。
以示例菜单为例为 `7 × 7 × 7 = 343` 个。

**这些组合的营养聚合、价格计算、券择优、排序全部在本地完成，不消耗 MCP 配额。**
单次完整交互的 MCP 调用次数约为 6-9 次，与候选组合数量无关。

若把每一步都放到线上计算，343 个组合将远超 600 次/分钟的限流阈值——
这是本作品采用"MCP 取数 + 本地算数"架构最直接的原因。
