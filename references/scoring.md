# 打分函数参考 · scoring.md

本文说明 MacroBuddy 如何从数百个候选组合中选出最终推荐，以及权重如何调整。
实现见 `scripts/macro_optimizer.py` 的 `evaluate()` 与 `optimize()`。

---

## 1. 总体约定

- **分数越低越好**。分数由各项惩罚加权求和，再减去优惠券利用加分。
- 每个方案的 `breakdown` 字典保存各分项得分，`reasons` 保存人类可读的理由。
  两者都会随方案一起返回，因此任何推荐都可以被逐步复盘。

```python
total = sum(breakdown.values()) - coupon_bonus
```

---

## 2. 默认权重

| 分项 | 权重 | 设计意图 |
|---|---|---|
| `kcal` 热量 | 45 | 热量是减脂/增肌的第一约束 |
| `protein` 蛋白质 | 30 | 缺口对目标达成影响最大，仅次于热量 |
| `fat` 脂肪 | 12 | 只罚超标，低脂本身不是问题 |
| `sodium` 钠 | 8 | 健康维度，但与单餐决策相关性弱于前三项 |
| `price` 价格 | 5 | 同营养水平下越便宜越好，不喧宾夺主 |
| `coupon_bonus` 用券加分 | 6 | 奖励把券用起来的方案 |

权重可通过 `ScoreWeights` 覆盖，无需改动算法代码。

---

## 3. 各分项公式

### 3.1 热量

落在 `[kcal_low, kcal_high]` 内不扣分；偏离则按偏离比例归一化，偏离 35% 触及满罚。

```
若 kcal < low:   d = (low − kcal) / low
若 kcal > high:  d = (kcal − high) / high
penalty = clamp01(d / 0.35) × 45
```

### 3.2 蛋白质

以 90% 需求线为基准，**缺口越大罚分越高**：

```
若 p < 0.9 × need:  penalty = clamp01((0.9×need − p) / (0.9×need)) × 30
若 p > 2.5 × need:  penalty = 0.30 × 30   # 极端过量，性价比下降
其余:               penalty = 0
```

> **实现注记**：早期版本在归一化时除以了额外的饱和系数 0.40，导致缺口 44% 即触顶，
> 44% 缺口与 78% 缺口得到完全相同的分数，丧失区分度。该缺陷由
> `selftest.py::test_score_penalties` 捕获并修正——测试用例断言
> 「缺口越大罚分越高」，两次运行分别得 30.0 与 30.0 从而暴露问题。
> 现版本直接以 90% 需求线归一化，蛋白为 0 时恰好满罚。

### 3.3 脂肪

只罚超标，以 115% 上限为起点：

```
若 f > 1.15 × cap: penalty = clamp01(((f − 1.15×cap) / (1.15×cap)) / 0.50) × 12
```

低脂不扣分——用户目标是控热量，不是凑够脂肪。

### 3.4 钠

```
若 s > cap: penalty = clamp01((s − cap) / (cap × 0.5)) × 8
```

超过 1.5 倍时，该组合会在 `_is_feasible()` 中被移出候选池，不进入排序。

### 3.5 价格

以候选池中的最高原价为基准归一化：

```
penalty = (payable / price_ceiling) × 5
```

### 3.6 优惠券加分

```
若已用券: bonus = 6 × clamp01(discount / (0.15 × subtotal))
```

即"券的减免达到订单金额 15%"时拿满加分。

## 4. 排序：字典序而非纯分数

```python
scored.sort(key=lambda s: (0 if s.in_band else 1, s.score))
```

**先按热量是否落在目标带内分档，再按分数排序。**

原因：纯分数排序下，6 分的优惠券加分足以把热量已经偏离目标带的方案顶到第一位。
在实测中曾出现推荐方案热量 650 kcal、而目标带上限为 648.6 kcal 的情况——
差值虽小，但它暴露的是**机制问题**：优惠力度可以压过营养达标。

本作品的产品立场是"营养优先"，因此用字典序把这一立场写进排序规则，
而不是靠调权重去逼近。附带好处是排序结果与权重调参解耦，调权重不会破坏优先级。

`ScoredCombo.in_band` 标记该组合是否落在带内，随方案一起返回，便于展示。

## 5. 候选池的三级回退

| 级别 | 条件 | 说明 |
|---|---|---|
| 一级 | 热量落在 `[low, high]` 且钠 ≤ 1.5×cap | 理想情况，三套方案均从此池选出 |
| 二级 | 热量在 `[0.78×, 1.35×]` 目标且钠 ≤ 1.5×cap | 无热量落在目标带内的组合时启用，设置 `relax_note` |
| 三级 | 热量 ≥ 0.6× 目标 | 进一步放宽，`relax_note` 说明已降级 |
| 兜底 | 取分数前 50 名 | 菜单与目标完全不匹配，`relax_note` 明确告知 |

**任何一级回退都会在 `relax_note` 中写明，并要求 Skill 如实告知用户**，
不允许静默降级。

---

## 6. 三套方案的选取

| 方案 | 选取规则 |
|---|---|
| 综合最优 | 候选池中排序第一 |
| 高蛋白优选 | 候选池中蛋白质最高；并列取实付更低、分数更低者 |
| 极致省钱 | 候选池中实付最低；并列取分数更低者 |

三套方案均从**同一个候选池**选出，因此都满足同一套营养底线，
"省钱"不等于"放弃营养"。

去重逻辑：若某方案与前一方案餐品组合完全相同，则跳过，避免输出重复项。
极端情况下可能只返回 2 套甚至 1 套方案。

## 7. 调参指引

| 想达成的效果 | 调整方式 |
|---|---|
| 更看重省钱 | 提高 `price` 权重、降低 `kcal` 权重（不建议降到 30 以下） |
| 控糖人群 | 提高 `fat` 与在 `ScoreWeights` 外补充的碳水权重 |
| 允许一定热量超标 | 放宽 `allocate_meal` 中的 `kcal_high` 系数 |
| 纳入甜品 | `optimize(..., allow_dessert=True)`，候选数翻倍 |
| 固定预算上限 | 在 `optimize` 前对 `combos` 按 `payable` 过滤 |

修改权重后请运行 `python3 scripts/selftest.py`，确保
`test_optimizer_end_to_end` 中的不变式（营养优先级、方案去重）仍然成立。
